# The generator vs Claude Code, on the same six specifications

Harness: `run_claude_baseline.py`. Each `prompts/prompt_<ident>.txt` is passed
**verbatim** to non-interactive Claude Code (`claude -p`, `--output-format
json`, empty working directory, no session persistence), plus one imperative
tail asking for the full runnable implementation. The result is then subjected
to the **same** gates as the generator: `functional_failures`,
`conformity_failures` and `conformity`'s prompt→surface check, from
`behavior_tests.named_prompt_suite`.

Claude's output is kept in `baseline/` (`baseline/<ident>/` for the CLI's own
default model, `baseline/sonnet/<ident>/` for `--model sonnet`), so every gate
can be re-run with `--reuse` without paying for another Claude run.

## The measurement had to be fixed first

Pointing the suite at code the same author did not write exposed **nine** checks
that encoded an unstated convention of this generator. Each was a real defect
of the *measurement*, not of the code being measured:

| # | check | convention it assumed |
|---|---|---|
| 1 | `cli_tool` optional output path | must be a NAMED `--option` (a positional is equally faithful) |
| 2 | `multi_module` id | must be a NAMED `--id` option (`show TASK_ID` is faithful) |
| 3 | `multi_module` service | must be a file named `*_service.py` |
| 4 | `multi_module` service ops | must be spelled `add`/`update`/`list` (`create_task` is faithful) |
| 5 | stub-marker proxy | bare `TODO` counts (an enum `TaskStatus.TODO` is not a stub) |
| 6 | repository ownership | every name word must be in the prompt (`find_potential_recurring`) |
| 7 | repository discovery | repositories are at the top level (a package nests them) |
| 8 | sweep placeholders | `x` for every option (a `-date` option needs a date) |
| 9 | `library_system` root | the first prompt token is always a sub-command, never the tool's NAME |

Nine has a full proof: `pyproject.toml` declares
`[project.scripts] library = "library_system.cli:library"`, and `main.py` says
it "is equivalent to installing the package and running `library`". Both
readings make the specification's literal line `library book add ...` work, so
neither is privileged; the gate now decides behaviourally.

Non-regression: after all nine corrections the generator still reports
**0 functional and 0 conformity failures on all six**, and
`run_repo_conformity.py` still passes 3/3.

## What Claude actually got wrong

Every remaining failure is a real, reproducible deviation — none is a gate
artifact, which is why each is listed with the evidence that established it.

**Both models read `library` as the tool's name.** Haiku's and Sonnet's
`library_system` expose `book add`, `member list`, `borrow`, `overdue` at the
root of the CLI. Under the gate's original reading that was 9 missing + 9 extra
commands; under the program-name reading it is exact. Sonnet declared the console
script; Haiku simply never created the group. This is the single largest source
of apparent non-conformance, and it is an **ambiguity in the specification**, not
a demonstrated defect.

**Haiku — `expenses` (FAIL 4 / FAIL 15).** The specification nests
`category` and `report` under `expense`. Haiku hoisted them to the top level
(`category add`, `report monthly`), flattened `expense recurring detect` into
`expense recurring`, and **added `expense delete`**, which the specification
never lists. 7 of the 14 declared paths are absent and 8 unrequested commands
are exposed. Verified by `cli.py --help`. This one is not ambiguous: the
specification's first tokens are `expense` AND `budget`, so no single token can
be the program name, and the nesting is stated literally.

**Both — a destructive command that hangs.** Haiku's `expenses budget delete`
and `multi_module delete` carry `--yes  Confirm the action without prompting.`,
so the invocation the specification gives —
`budget delete --category-id --month`, `delete <id>` — **blocks forever**
instead of completing (measured: 90 s timeout, exit 124). Haiku scored
`multi_module` FAIL(1) on exactly this. Adding a confirmation is defensible UX;
making the specification's own command line non-terminating is not.

**Haiku — `library_system` over-generation (FAIL 2).** The CLI exposes
`author add` and `author list`; the specification asks for no author command at
all. This is the defect class this project fixed for itself in an earlier pass
(the surface is now read from the prompt, S19).

**`expenses --category` is an id for one implementation, a name for the other.**
The specification writes `expense add --amount --description --category` without
saying which. The gate passes `1`; Haiku answers `✗ Category '1' not found`, and
its command works end to end with a category NAME (`--category Food` exits 0).
Left as an ambiguity, not scored as a defect.

**Sonnet: nothing.** All six specifications produce a CLI that passes both
gates, and three of them are installable packages (`pyproject.toml`,
`[project.scripts]`, repositories under `repositories/`).

## What this says

* **The gate is the real contribution.** The generator ties Sonnet on the two
  axes the gate measures, at 4B parameters and zero API cost. It does not tie
  Sonnet on everything a person would notice (number of files, packaging,
  documentation, defensive style) — only on the two questions the suite asks.
* **The suite is now measurably not tautological.** It found nine of its own
  defects only when pointed at a foreign implementation, and it still
  discriminates: it passes the generator and Sonnet, and fails Haiku on three
  real deviations.
* **The specification itself is the weakest link.** Two of the graded
  "failures" (the `library` program token, and id-vs-name for `--category`) are
  ambiguities a human reviewer would have to adjudicate, not defects. A
  conformance suite cannot be sharper than the specification it encodes.
